# 产品与技术方案


## 第三章  产品与服务

本章回答"我们到底做出来了什么"。撰写商业计划书时，按"产品定位 → 已实现的功能 → 使用流程 → 产品边界 → 一次记录输出什么"的顺序组织。

**本章所有功能都标注了完成状态。已经做出来的，本章给出的是可以现场演示的真实行为；尚未做的，明确写在 3.5 的边界里。**


### 3.1 产品定位与形态

肤镜是一本**"认身体"的家庭皮肤手账**。它的定位可以概括为三句话：

- **对身体，它是一个位置索引。**不是按时间堆照片，而是按身体位置组织记录。在人体上点一下，那一处的历史就都出来了。

- **对变化，它是一台比较器。**核心价值不在"存了什么"，而在"能比出什么"：并排与滑动的前后对照，加上复查时按上次构图对齐拍摄，让"变好还是变坏"第一次变得看得出来。

- **对隐私，它是一间上锁的屋子。**照片默认不写入档案；整个应用在本地运行，运行期与外界没有任何网络通信。**这一点可以当场验证，不需要用户相信我们的承诺。**

产品的形态是一个本地网页应用，由四个部分构成：

| 组成部分 | 形态 | 作用 | 状态 |
|---|---|---|---|
| 三维人体手账 | 浏览器内实时渲染的三维人体（Three.js + 本地 GLB），支持旋转、缩放、正背面切换与身体点选 | 作为空间索引：把每条观察记录挂到身体的具体位置上，书签会随视角变化自动隐藏被遮挡或朝向背面的标记 | **【已完成】** |
| 观察记录 | 照片（导入或现场拍摄）+ 症状点选 + 持续时间 + 变化描述 + 备注 | 把"这一次"完整记下来；照片留存默认不勾选，这条规则写在数据层而非界面层 | **【已完成】** |
| 对照与复查 | 并排对照、滑动对照、文字症状差异表；复查时以上次照片作为半透明构图参考 | 解决"可比性"问题——这是整个产品最核心的两个功能 | **【已完成】** |
| 家庭成员与本地档案 | 成员切换与新增、复查计划、本地档案导出与删除 | 让一位家长可以分别管理自己、孩子与老人的记录，避免张冠李戴 | **【已完成】** |
| 端侧识别 | RK3576 边缘设备上的皮肤影像质量评估与识别 | 为记录补充"疑似方向"与"下一步建议" | **【下一阶段】尚未接入** |

### 3.3 三步使用流程

产品的使用流程刻意压到三步。**请注意第三步的诚实设计：在没有接入识别模型时，真实照片走到的界面不会给出任何结论。**

- **第一步：找。**打开网页，先选择家庭成员（首次使用直接建立成员，没有注册和登录页面）。在三维人体上点一下问题部位，系统确认部位与左右侧，建立或继续一条位置记录。也可以走"按部位列表查找"的文字入口。

- **第二步：记。**导入已有照片或现场拍摄；点选本次的感受、持续时间与变化，可补充文字备注。系统会把照片统一重编码、去掉元数据。

- **第三步：看。**进入观察页，确认成员、部位、日期与影像归属；选择是否把照片保存到本地手账（**默认不勾选**）；保存后返回该部位的手账，新记录在时间线上突出显示。此后可以在"前后对照"里比较两条记录，或从复查计划发起一次带构图参考的复查拍摄。

流程链示意（可直接用于 PPT）：

```
在人体上定位部位  →  导入照片 / 现场拍摄（质量与格式校验）
        ↓
点选症状 · 持续时间 · 变化  →  查看本次观察
        ↓
选择是否留存照片（默认不留）  →  保存为一条位置记录
        ↓
前后对照（并排 / 滑动）  →  复查拍摄（上次构图半透明参考）
        ↓
复查完成  →  该部位待办自动移除  →  时间线继续累积
```


### 3.4 一次记录会看到什么

为了让评委直观理解产品，下表说明一条记录在界面上由哪些部分组成。**其中"识别结论"一栏当前是明确留空的，这本身就是产品设计的一部分。**

| 组成 | 内容 | 当前实际行为 |
|---|---|---|
| 归属确认 | 成员、部位、日期与影像 | 明确显示这条记录属于谁、哪一处、哪一天，避免记错人 |
| 影像 | 本次照片（如已提供） | 导入或拍摄的照片经校验与重编码后显示 |
| 症状 | 感受、持续时间、变化 | 用户点选的固定选项，构成结构化记录 |
| 识别结论 | 疑似方向、可读的观察依据、不确定性、下一步建议 | **当前明确显示"本次尚未进行 AI 识别"，并说明检测服务尚未接入、不会生成病名、置信度或治疗建议** |
| 留存选择 | "将本次照片保存在本地手账" | **默认不勾选**；不勾选时只保存文字，刷新后这张照片不存在 |
| 后续动作 | 前后对照、发起复查、调整复查计划 | 把一次记录接进连续观察的循环 |

**为什么要把"识别结论"做成明确留空而不是填一段示例文案？**因为这是我们对自己产品的基本要求：在模型经过真实数据验证之前，不给用户任何看起来像结论的东西。原型里唯一出现"湿疹 / 皮炎类表现"字样的地方，是用户主动点击"使用内置示例"后显示的演示记录，页面上有"示例结果 · 非诊断"的明确标记，且与真实用户输入完全隔离。


### 3.5 产品边界：我们不做什么

明确说清"不做什么"，是让评委相信团队想清楚了的方式。本项目边界有五条。

| 不做什么 | 理由 |
|---|---|
| 不做诊断、不给处方<br>（不输出病名结论、不推荐用药） | 本项目是帮助用户记录与观察的工具，不是医疗器械。治疗决策依赖完整临床信息与医生的专业判断，超出本项目的能力边界，也带来直接的医疗风险 |
| 不做社交与内容社区<br>（不做病例分享、不做经验交流） | 皮肤照片是敏感的个人身体信息，任何形式的公开分享都会把用户置于风险中。本项目的数据从设计上就是"只在这台设备上"，不做流通 |
| 不做通用健康管理平台<br>（不做用药提醒、计步、饮食管理） | 注意力是团队最稀缺的资源。聚焦"一处皮肤随时间的记录与比较"这一个垂直场景，才可能真正做到位 |
| 不做需要上传云端才有价值的方案 | 一旦照片必须上传，产品最核心的隐私主张就不成立了。本项目的本地优先架构是产品定义，不是实现细节 |
| 不追求覆盖所有皮肤病<br>（不做全病种宣称） | 识别范围必须由模型在真实数据上的验证结果决定，而不是先宣称再想办法实现。**范围未验证之前，我们不做承诺** |

**关于最后一条需要特别说明**：本项目题目中包含"智能识别与辅助诊断"，而当前版本尚未接入识别模型。我们没有通过缩小宣称、也没有通过编造结果来抹平这个差距，而是把它写在明处：产品已经完成的是一套**能被验证的记录、对照与隐私架构**，识别是明确规划的下一阶段。在答辩中这一点必须主动讲清。

## 第四章  技术方案与实现

本章是全书技术部分的核心。**本章只写已经实现的代码，不把计划写成功能。**4.1 到 4.5 是已完成并有测试支撑的实现；4.6 是下一阶段的端侧识别设计，明确标注为未完成。

阅读建议：4.5 的隐私架构是本项目最有说服力的技术部分，也是答辩中可以直接现场验证的部分；4.8 的评测结果全部可复现；4.9 的诚实声明用于答辩防守。


### 4.1 总体架构：本地优先

本项目在架构上做了一个也许不常见、但非常明确的选择：**不设服务端。**应用的全部逻辑在用户的浏览器里运行，全部数据存在用户本机的浏览器数据库中。这个选择不是为了省事，而是为了让隐私主张成立——**如果系统里根本不存在一个能接收照片的服务器，那么"照片不会上传"就不再是一句需要被相信的承诺。**

```
用户浏览器（本地）—— 全部逻辑与数据都在这里
    界面层  首页手账 / 新检查 / 观察结果 / 拍摄 /
            前后对照 / 复查计划 / 家庭成员 / 本地档案
        ↓
    三维层  Three.js 人体渲染 · 射线拾取 · 书签投影 · 二维降级
        ↓
    逻辑层  档案关系与保存规则 · 图像输入校验与重编码
        ↓
    存储层  IndexedDB 本地档案（照片默认不写入）

    ╳  运行期与外界无任何网络通信（有测试断言）

下一阶段：RK3576 端侧识别  ┄┄┄ 尚未接入
```

这一架构带来三个直接结果，它们同时也是本项目的技术特点：**免注册免登录**（没有账号体系，因为不需要）；**离线可用**（打开就能用，不依赖网络）；**可验证的隐私**（用户可以在浏览器开发者工具里看到没有任何外部请求）。


### 4.2 三维人体位置索引

本项目的技术难点不在于"画一个人体"，而在于让**人体成为一个可用的空间索引**：用户点在哪里，系统就要准确知道那是哪里；转视角的时候，标记要跟着动、并且不该显示的标记必须消失。

| 技术点 | 实现方式 | 解决什么问题 |
|---|---|---|
| 模型与材质 | 加载本地 GLB 人体网格（来自 MakeHuman 的 CC0 基础网格，487,496 字节），遍历时释放模型自带材质并统一替换为一个共享的哑光材质，重算法线 | 统一视觉风格（哑光雕塑感），同时避免多材质带来的渲染开销 |
| 交互旋转与缩放 | 轨道控制器；限制俯仰角与距离区间，关闭平移，保证用户不会把人体转丢或缩到看不见 | 让非技术用户也能稳定操作，不会"把界面弄坏" |
| 身体点选 | 在指针抬起时（左键且拖动距离不超过 5 像素，与"旋转"手势区分开）从相机发射射线，与人体网格求交；把交点沿法线外移 0.035 后交给业务层，并自动推断所属身体区域 | 让"点一下身体"成为可靠的定位方式，而不是靠用户描述部位 |
| 书签投影 | 每帧把部位坐标投影到屏幕坐标，换算成百分比定位；朝向背面（法线与视线夹角判定）、移出画面、或被人体遮挡时隐藏标记 | 解决"标记漂浮在人体外面"的视觉错误——这是三维界面最常见的穿帮 |
| 遮挡判定节流 | 遮挡检测（再次射线求交）按 100 毫秒节流 | 在保证视觉正确的前提下控制每帧开销 |
| 正背面切换 | 沿模型外围做角度插值的缓动旋转，而不是穿过模型中心；系统开启"减少动态效果"时直接切换不做动画 | 避免"穿模"的观感，同时尊重无障碍设置 |
| 二维降级 | WebGL 初始化失败、模型加载失败或上下文丢失三种情况自动降级为二维正视图 + 文字部位列表；二维下用一套手写的仿射映射把部位坐标落到示意图上 | **保证低性能设备或不支持 WebGL 的环境里，核心流程依然可用** |
| 资源释放 | 组件卸载时停止动画循环、停止监听尺寸变化、释放几何体与材质、销毁渲染器并强制丢弃 WebGL 上下文；模型在卸载后才加载完成时，也会把迟到的资源释放掉 | 避免长时间使用后显存泄漏导致页面卡死 |


### 4.3 图像输入的规范化与校验

用户提供的图片是不可信的输入。本项目在图片进入系统之前设了四道检查，并在通过之后统一做一次规范化重编码。**这一节的每一条都有对应的测试。**

| 检查项 | 规则 | 为什么需要 |
|---|---|---|
| ① 体积 | 单个文件大于 0 且不超过 12 MB | 防止超大文件卡死页面 |
| ② 类型与扩展名 | 类型必须是 JPEG / PNG / WebP，且文件名扩展名必须与之相符 | 两道条件都要满足，避免只改扩展名的伪装文件 |
| ③ 文件头签名 | 校验 PNG、JPEG、WebP 的魔数字节，**并要求签名与声明的类型一致** | 这是挡住"改了扩展名的 SVG"这类伪装的关键一道。有测试用伪装成 JPEG 的 SVG 验证其被拒绝 |
| ④ 真实解码 | 实际解码图片并检查宽高：像素总数不超过 3600 万、宽度与高度不能为 0 | 只有真正解码成功才说明这是一张能处理的图片 |
| ⑤ 规范化重编码 | 通过检查后统一重编码为 JPEG，长边不超过 2048 像素，质量为 0.92，绘制在不透明白底上 | 统一格式与尺寸，同时**顺带去掉了原图的 EXIF 元数据**（重编码后原元数据不再存在） |

关于第 ⑤ 条需要诚实说明一点：**去元数据是通过重编码自然实现的，而不是一段显式的"清除 EXIF"代码。**结论（保存下来的副本不携带原图元数据）是正确的，但实现方式是间接的。如果后续要把它变成一条可对外承诺的保证，应当补一段显式的处理与相应的测试。


### 4.4 本地存储与保存语义

把数据放在用户自己的浏览器里，会带来一系列"服务端架构不需要操心"的问题：写一半失败了怎么办？用户切标签页了怎么办？数据被改坏了怎么办？本项目对这些情况都做了明确处理。

| 问题 | 本项目的处理 | 为什么重要 |
|---|---|---|
| 存储位置 | IndexedDB，库名为 dermascope-local-journal-v1，单一对象仓库与单一键，整份档案作为一个结构化的整体读写 | 结构简单、事务语义清晰；代价是每次保存都会重写整份档案，照片很多时会成为容量与性能的限制（见 4.9） |
| 写入前校验 | 保存前先对整份档案做一次完整校验（字段、词表、坐标数值、时间戳、照片格式、成员归属），校验不通过直接拒绝写入 | **从机制上保证坏数据无法覆盖好数据** |
| 保存成功才提示 | 先把改动写入存储、事务完成之后，才显示"保存成功" | 避免"界面说保存了、其实没存上"这类最伤用户的错误 |
| 写入失败保留草稿 | 写入出错时不清空用户已填内容，可重试 | 用户填了半天症状和备注，不能因为一次存储抖动就全丢 |
| 跨标签页写入 | 支持 Web Locks 的浏览器上，用一把命名锁把不同标签页的写入串行化；不支持的浏览器则提示刷新查看 | 防止两个标签页同时保存导致互相覆盖 |
| 未保存离开保护 | 存在草稿时切换页面或关闭页面会先询问；确认放弃后才丢弃 | 避免"手一滑点错了，记录没了" |
| 坏数据保护 | 读到无法识别的档案时，显示读取错误并明确说明现有数据未被覆盖，而不是用示例数据顶掉 | 用户的历史记录比"应用看起来正常"重要得多 |
| 照片留存默认关闭 | 照片只有在用户明确勾选后才写入档案；**这条规则写在数据层，不只是界面上的一个复选框** | 隐私相关的默认值不能依赖界面，必须由数据层强制 |
| 删除的边界 | 删除照片保留文字；删除成员级联删除其记录与计划（删除前提示影响范围）；删除操作不影响用户电脑里的原始文件 | 让"删除"的含义对用户是可预期的 |


### 4.5 隐私架构：三条可验证的红线

本项目的隐私设计不是原则表述，而是三条**在代码层面成立、并且可以被当场验证**的约束。**这是全书最值得在答辩中现场演示的部分。**

| 红线 | 技术实现 | 如何验证 |
|---|---|---|
| 红线一：运行期没有任何外部网络通信 | 页面内容安全策略限制为 default-src self；源码中不存在任何发起网络请求的代码（无 fetch、无 XMLHttpRequest、无 WebSocket、无埋点上报）；摄像头权限策略只申请视频、明确禁止麦克风；引用策略关闭 referrer | **当场打开浏览器开发者工具的网络面板，走一遍完整流程，可以看到没有任何外部请求。**自动化测试同样记录了全部非 GET 请求并断言为空 |
| 红线二：照片默认不进入档案 | 照片留存复选框默认不勾选；更关键的是，**保存逻辑在数据层检查这个开关**，未勾选时照片字段根本不写入；导出的 JSON 默认也不含照片，需要明确勾选才包含 | 保存一条不带照片的记录并刷新，照片不存在；导出档案查看 JSON，照片字段为空。两条都有自动化测试覆盖 |
| 红线三：档案在结构上容纳不了"诊断结论" | 记录中存放分析结论的字段，取值被限制为"未分析"和"示例"两种；**该取值不是由界面决定，而是由数据层根据记录来源推导出来的**，任何未经模型验证的结论在结构上无法写入档案；校验逻辑会拒绝其他取值 | 尝试构造一条带外部图片地址或非法结论取值的档案，校验会直接拒绝（有单元测试验证） |

这三条红线的共同点是：**它们不是"我们承诺不做"，而是"我们做不到"。**一个承诺需要被相信，一个架构只需要被检查。在隐私这件事上，后者才是用户真正能得到保障的形式。

同样需要诚实说明边界：本项目免登录，因此"家庭成员"是**记录分组**，不构成身份权限隔离；本地数据没有加密，能访问这台电脑与这个浏览器的人就能看到档案。这些限制已经写进产品界面本身，而不是藏在文档里。


### 4.6 下一阶段：端侧识别的接入设计

**本节内容尚未实现，是明确规划的下一阶段工作。列出它是为了让评委会看到我们对技术路线有清晰的判断，而不是把计划当成已完成的能力。**

本项目题目中的"边缘计算"，落点是把识别放在本地设备上，而不是把照片送到云端。这个选择与 4.5 的隐私架构是一致的：如果照片必须离开设备才能被分析，前三条红线就同时失效。

```
训练阶段（开发机 / 服务器）
    皮肤影像数据准备（公开数据集 + 合作机构自建数据）
        ↓
    训练影像质量评估模型与疑似方向分类模型
        ↓
    导出 ONNX → RKNN 工具链转换与量化
        ↓
部署阶段（RK3576 边缘设备）
    拍摄影像 → 本地质量评估 → 不合格则明确提示"无法分析"
        ↓
    质量合格 → 端侧推理 → 疑似方向 + 可读的观察依据
        ↓
    不确定或超出能力范围 → 明确推荐就医，而不是给结论
        ↓
    结果返回手账（本阶段唯一需要确定的外部接口）
```

| 待明确的问题 | 说明 | 状态 |
|---|---|---|
| 设备与本机的连接方式 | 浏览器与 RK3576 之间通过什么方式通信（本机服务、局域网、还是设备直连）；**注意当前页面的安全策略会阻止对外连接，接入时需要一并调整** | 【下一阶段】 |
| 支持的病种范围 | 由模型在真实数据上的验证结果决定，而不是先宣称范围再想办法实现 | 【下一阶段】 |
| 图像质量评估与拒识条件 | 什么情况下判定"无法分析"，以及如何向用户解释——这一条比识别精度本身更重要 | 【下一阶段】 |
| 结果如何进入档案 | 需要在数据层扩展"分析结论"字段的取值，并保证只有经过模型验证的结论才能写入 | 【下一阶段】 |
| 数据与伦理 | 若使用合作机构的真实影像，须先取得知情同意并通过相应的审查流程 | 【下一阶段】 |

### 4.9 技术边界与诚实声明

本节内容建议直接翻译成答辩话术。主动、准确地说明边界，比含糊其辞地宣称"什么都行"更能赢得评委的信任。

- **关于识别功能**：当前版本没有接入任何识别模型，不产出病名、概率、置信度或治疗建议。真实照片走到的界面会明确显示"本次尚未进行 AI 识别"。这是我们刻意的选择，不是遗漏——在模型经过真实数据验证之前，我们不用假结果填充产品。

- **关于"辅助诊断"**：本项目定位是帮助用户记录与观察的工具，不是医疗器械，不提供诊断。题目中的"辅助诊断"指的是为就医决策提供依据（例如"这处连续三周没有好转，建议就诊"），而我们目前提供的依据来自**用户自己的连续性记录**，而不是算法结论。

- **关于存储与容量**：整份档案以单条记录的形式存放，因此每次保存都会重写整份档案；照片以数据地址的形式内嵌在档案里。在照片数量很多、单张很大的情况下，这会成为一个容量与性能的限制。我们尚未做长期的容量评测。

- **关于 EXIF 元数据**：保存下来的照片副本确实不携带原图元数据，但这是重编码带来的结果，而不是一段显式的清除逻辑。把它作为对外承诺之前，应当补上显式实现与测试。

- **关于跨标签页与账号**：跨标签页写入在支持相应能力的浏览器上会被串行化，不支持的浏览器需要刷新才能看到其他页的修改。产品免登录，因此成员只是记录分组，不构成权限隔离；本地数据未加密，能访问这台电脑的人就能看到档案。

- **关于测试范围**：浏览器流程测试目前只覆盖 Edge，单工作进程、无重试；摄像头流程使用合成媒体流与权限模拟，**没有用实体摄像头联调过**；尚未做多浏览器与完整的无障碍审计。

- **关于三维性能**：人体模型与三维库的体积、低性能设备上的流畅度、长期运行的稳定性，都还没有专项评测。产品提供了二维降级路径，但降级路径本身在真实低端设备上的表现同样待测。
